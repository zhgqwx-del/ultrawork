# 开始一项变更

1. 读 `AGENTS.md`、`docs/engineering.md` 和需求来源。沿能力规格、接口、代码和测试找出现状、目标及要保留的行为。列出影响实现的待定业务规则及对应 `REQ`、`AC`。
2. 若使用 Git，先核对当前分支、未提交变更、开发基线、合入目标和对应提交。按任务、已有变更或 PR、仓库约定确定目标，不从功能分支的 upstream 或名称直接猜合入目标。以远端为基线时默认 fetch 已确认的远端并记录解析后的 SHA；离线或仅用本地基线时注明来源和未刷新状态。按约定创建或复用分支，需要隔离时使用工作树；保留用户已有改动。参考 `docs/stdd/git-workflow.md`。
3. 复用已有变更目录。新变更用 `python3 -B scripts/new_change.py <变更ID> '<标题>'`。四角色一起评审时加 `--roles`，涉及跨模块、接口兼容、迁移或重要取舍时再加 `--design`。已有变更可按需使用 `docs/stdd/templates/design.md` 补充技术设计。
4. 默认先在 `tasks.md` 的「实施方案」写一份可评审的短方案。写清改哪些入口和组件、保留什么、关键取舍与风险，以及按哪些场景和命令验收。从项目构建配置和现有测试核对实际入口，记录适用的基线检查及已知失败。在 `change.md` 保留分支、基线引用与 SHA、合入目标、同步策略；有修复回合或多仓发布要求时记录对应目标，收尾继续沿用。小改动可以用同样的内容记录在工单或 PR。复杂细节写入 `design.md`。
5. 查看 `docs/stdd/decisions-and-discussions.md`（如有）和项目已有记录。单次问题留在 `change.md`。跨角色、多轮或跨变更讨论按项目约定单列，缺省用 `docs/discussions/`。需要长期约定时先查 ADR 目录和既有决策，沿用项目指定路径或已有的 `docs/adr/`、`docs/decisions/`。现有记录优先复用。从 `change.md` 的「关联讨论与 ADR」链接相关文件或工单，标明本次影响及待确认项。
6. 先把方案和相关验收口径交给用户或项目负责人确认，记录确认来源或待决项。团队已有同范围的确认记录时直接沿用。支持规划模式的宿主可在此阶段使用规划模式。确认前推进规格、设计和准备工作，确认后交给 `stdd-delivery` 写测试与实现。
