# Git 基线、分支与提交前检查

将实际约定记在 `AGENTS.md` 或工程文档中。已有项目沿用自身策略；未另行指定时，准备提交或 PR 的收尾默认刷新目标，并对适合改写的本次提交执行 rebase。任务中已有明确要求时按指定的基线和目标执行，将分支、基线 SHA、真实合入目标和同步结果留在变更记录。

Ultrawork 的常规主干是 `main`，[跨平台 CI](../../.github/workflows/ci.yml)覆盖主干推送和目标为主干的 PR。每项变更在开工时从任务或 PR 核实实际目标。提交信息和收尾步骤见 [仓库协作约定](../../CLAUDE.md)，合入前检查见[质量门禁](../quality-gates.md)。

| 约定 | 团队需写明什么 | 缺省行为 |
| --- | --- | --- |
| 开工基线和合入目标 | 每类任务的基线、本地或远端引用、目标分支 | 识别当前工作区和已有变更，不猜测其他分支 |
| 同步方式 | 远端、同步时机、rebase 或 merge 策略及离线安排 | 以远端为基线时刷新引用；收尾按下方提交关系同步 |
| 开发分支 | 使用当前分支、新分支或工作树，以及命名规则 | 保留当前分支 |
| 提交前检查 | 定向测试、构建、lint、全量检查及适用范围 | 使用仓库现有入口记录实际运行结果 |
| 提交整理与合入 | 可改写的分支、squash 的位置及推送方式 | 保留已发布公共历史；个人变更按下方条件 rebase，squash 按项目策略 |

使用短期功能分支的团队，可以在仓库约定里写「从 `origin/main` 建 `feat/<变更名>`，打开 PR 到 `main`，合入时由 PR 执行 squash」。使用发布分支的团队可以按任务类型列不同基线和目标。

## 开工

1. 检查 `git status --short --branch`，从任务、已有变更或 PR、仓库约定依次确定基线和目标。功能分支的 upstream 常是自身远端分支，不能直接当作合入目标。基线和目标不同，例如修复版本分支时，分别写清；无法确定时继续独立的规划和检查，只补问缺少的信息。
2. 以远端为基线时默认 fetch 已确认的远端，再解析引用得到 SHA。需要推进本地基线时，使用项目约定的快进方式。离线、无远端或仅使用本地基线时写明实际来源及未刷新状态，不能声称已是远端最新。
3. 按约定复用或创建开发分支。需要隔离，且当前工作区已有改动时，优先考虑从选定基线建立独立工作树。保持原有改动与暂存区可追溯。仓库没有明确分支约定时，可在现有工作区先起草方案。
4. 交付可评审的实施方案。宿主支持规划模式时可以进入该模式，确认记录来自用户、需求负责人或团队已有的评审。

## 收尾同步

### 1. 核对工作区与恢复点

- 检查当前分支、暂存区、未暂存及未跟踪文件，识别已有 rebase、merge 或 cherry-pick 的归属。续接本次已授权流程时沿用原记录，不另起同步，也不为清理状态取消其他人的操作。detached HEAD 时先确定交付分支。
- rebase 前保持干净工作区。按任务已有授权整理本次改动；有权临时存放时记录保存和恢复方式。不要把无关改动一并提交或静默 stash。不能安全整理时保留现场，先做独立检查，不对该工作区执行 rebase。
- 记录同步前分支和 HEAD。改写前创建未占用的本地备份引用，保留恢复入口；未确认同步及推送结果前不清理该引用。已发布分支还需核对远端提交和共享状态。

### 2. 刷新并固定目标

下面以 `origin/main` 为例，远端和分支必须换成项目实际合入目标。显式 refspec 确保更新要使用的远端跟踪引用，然后固定本轮目标 SHA。

```sh
stdd_remote=origin
stdd_target=main
git fetch "$stdd_remote" "refs/heads/$stdd_target:refs/remotes/$stdd_remote/$stdd_target"
```

仅在 fetch 成功后解析引用：

```sh
stdd_target_sha=$(git rev-parse --verify "refs/remotes/$stdd_remote/$stdd_target^{commit}")
```

解析成功后才进行后续比较。记录目标引用、SHA 和刷新结果。fetch 失败、引用不存在或没有共同祖先时，说明原因并保留现场，不使用旧 SHA 宣称已同步，不使用 `--root` 或猜测其他目标继续。

### 3. 按提交关系执行

使用 `git merge-base --is-ancestor <目标SHA> HEAD` 及反向比较判断关系；退出码 1 表示非祖先，其他错误需单独处理。始终使用本轮固定的目标 SHA。

| 关系与分支条件 | 操作 |
| --- | --- |
| 目标是 HEAD 的祖先，含两者相同 | 已包含该目标版本，无需 rebase |
| HEAD 是目标的祖先，当前分支仅落后 | 在当前分支执行 `git merge --ff-only <目标SHA>` |
| 双方均有独有提交，待重放部分均未发布 | 保存恢复点后执行 `git rebase <目标SHA>`，只重放待交付的本次提交 |
| rebase 会改写已发布的个人分支提交 | 先核对远端新增内容、分支所有权及项目允许改写的约定，满足现有授权再执行 |
| rebase 会改写他人依赖的共享历史 | 按项目 merge 或协调流程同步；不能将其视为默认个人分支 rebase |

对共享主干只整理尚未发布的本地提交，保留已发布公共历史。存在额外提交、合并提交或堆叠分支时先核对待重放范围；不能确定哪些属于本次时先澄清范围，不盲目重放整个分支。项目规定 merge 时沿用 merge 策略，记录与本次验收关联的目标版本。

### 4. 冲突与续接

rebase 暂停后，用 `git status`、`git diff --name-only --diff-filter=U` 和当前补丁确认冲突。逐文件核对双方意图、已确认规格和场景 ID；保留双方仍适用的功能及测试。解决后检查差异，再 `git add <已解决文件>`、`git rebase --continue`，重复至完成。

不要批量选 ours/theirs、删除断言或 `git rebase --skip` 来绕过冲突。有新的业务取舍或无法判断的语义冲突时，记录冲突文件、双方意图、已完成步骤和待决定事项，暂停该候选的提交与推送。需要撤回本次 rebase 时使用 `git rebase --abort`；它回到本次 rebase 开始前，备份引用仍可用于复核，不用 `reset --hard` 清理现场。

## 同步后的验证与交付

1. 先恢复本次临时保存的改动，使用记录的保存标识，避免盲目恢复 stash 栈顶。恢复有冲突时保留保存记录，按同样的规格和双方意图处理，完成前不开始最终验收。然后核对候选差异、规格、任务、讨论和 ADR 链接；依赖或锁文件变化时按项目命令同步依赖，避免把缺包当作行为回归。
2. 运行定向验收及项目要求的构建、静态检查、回归和手工验收。记录实际退出状态、用例数量、观察结果及受测 HEAD；未提交代码还需写明工作区差异。同步前的证据保留为历史，最终候选的结果另行记录。仅追加验收文档的提交说明其与受测内容的关系，不虚构事后 SHA 已经运行过测试。
3. squash 默认沿用项目合入流程；本地整理只作用于已授权范围。提交整理后核对最终候选，受测内容变化时复跑对应检查。必跑检查失败或必验场景待验时，按项目约定标记未就绪，仍可交付如实记录的报告。
4. 提交、推送及创建 PR 按已有任务授权执行。普通推送优先；已发布个人分支需要改写远端时，核对并保存经过审核的远端预期 SHA，按项目约定使用 `--force-with-lease=<远端分支完整引用>:<预期SHA>`。远端变化导致拒绝时重新检查他人提交，不能用新的未审核 SHA 刷新 lease 后直接重试，更不能以强推覆盖共享主干。
5. 如果测试期间目标继续前进，更新目标后重新同步并复验。远端持续变化或同一错误未解决时，记录最后核对的目标 SHA、候选状态和继续方式，交接仍未完成的同步，不循环重试或声称已与最新目标兼容。

Git 命令语义见 [rebase](https://git-scm.com/docs/git-rebase)、[fetch](https://git-scm.com/docs/git-fetch) 和 [push](https://git-scm.com/docs/git-push)。这些是 Agent 执行步骤；脚手架的 `git_range.py` 只读取差异，不自动执行 Git 同步。
