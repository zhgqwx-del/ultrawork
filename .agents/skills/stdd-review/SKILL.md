# 审查变更

1. 根据用户请求、PR 目标或仓库约定确定范围，解析并记录目标和候选 SHA，不用同名远端分支替换用户指定的本地候选。要求审查远端最新版本时先刷新相应引用，失败则说明实际采用的本地版本。审查已提交分支时，用 `python3 -B scripts/git_range.py --merge-base <目标引用> <候选引用>` 定位增量；审查工作区时同时查看已暂存、未暂存及相关未跟踪文件，说明其与 HEAD 的关系。
2. 先扫改动范围和依赖，再读取目标 SHA 对应的评审规则（如有）、已确认的规格和实施方案。审查非当前分支时，从候选 SHA 读取文件，例如 `git show <候选SHA>:<路径>`，避免将当前工作区当作候选。沿变更查调用方、删除文件的残留引用、数据状态和副作用，核对相关的边界、失败、兼容、并发及权限风险。大变更优先检查受影响的关键入口，并写明未深入审查的范围。核对是否混入无关改动，以及删改断言和 CI 的实际理由。
3. 将 `REQ-*`、`AC-*`、测试和证据关联起来，检查受测提交是否对应当前候选。核对变更所引讨论和 ADR 的状态、影响及可达性。缺少证据时，按任务范围复跑关键用例或列出待验证项。
4. 按影响给出可操作的发现，附候选文件与行号、触发条件、受影响场景和可观察后果；区分已确认缺陷和待复核假设。没有发现时如实说明，并列出实测范围和证据限制。审查保持只读，不切换用户分支、rebase 或自动修复；复跑非当前候选时使用隔离副本，并记录实际受测版本。
