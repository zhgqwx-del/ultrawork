# ADR-067: deckcraft 文本对比度机器门禁（把主观 R4 升为物理下界）

- 状态：Accepted（✅ 已实现，2026-07-23）
- 日期：2026-07-23
- 关联：discussions/052（根因 + probe 校准数据 + 三方案对照）、ADR-066（密度轴——同一「有主观检查、无机器下界」结构缺口的另一半）、ADR-061（deckcraft 为唯一默认做 PPT 技能，质量兜底无退路）

## 背景

ADR-066 Phase B 真机验收时暴露一个与密度轴正交的缺陷：`presentation` 档某页 S04 两栏的**栏头**被模型染成 `--c-on-dark`（深底页专用浅字）却留在浅卡片 `--c-bg2` 上 —— 对比度 **1.10:1，几乎隐形**（截图实证，见 discussions/052 §一）。

**根因不是引导缺失**：`assets/templates/layouts.html` 的 S04 栏头示范是正确的 `--c-primary`，三个内置 example 的 S04 栏头**全部** `--c-primary`（9.96:1）。即「正确模板 + 正确 few-shot 齐备，模型仍偶发偏离」。本该拦下它的 `visual-review.md` R4「对比可读」是**评审子代理的主观判断**，真机那轮漏掉了。

这与密度侧当初「有 R3 主观留白检查、却无机器密度下界」是**同一类结构缺口**：主观检查不可靠，缺一道机器门禁兜底。ADR-066 用 O9 补上了密度轴的机器下界，本 ADR 补对比度轴。

## 决策

**扩 `probe_overflow.py`（它本就在 headless Chrome 里渲染每一页），逐可见文本元素实测 WCAG 对比度并设下界** —— 即 discussions/052 的方案①。不选方案②（`validate_deck` 静态查 on-dark 用在浅底）：它只逮这一种错法，逮不到任意自定义浅色；不单独用方案③（引导硬化），因为本次证明了纯引导不保险 —— 但引导仍作为便宜的补充一并做了。

### D1 — 测「painted 真值」，不测源码
前景取 `getComputedStyle().color`；背景是**合成值**，且合成的对象是**真实绘制栈**：对元素中心点 `document.elementsFromPoint()` 取该点的完整绘制栈（既含祖先、也含压在上面的重叠元素），从 `el` 往下由底向上叠在不透明白底上。祖先的 `opacity` 折进字色 alpha。

**为什么不是只走祖先链**（首版就是，后被自测推翻）：浅字绝对定位压在一个**兄弟**深色块上时（真实观感完全可读），祖先链只能看到卡片的浅底 → 判 1.00:1 **误杀合法设计**。对本门禁而言假阳性是代价更高的失败模式（它会拦住正确的 deck），故改用命中测试取真实绘制栈。命中测试看不到 `el` 时（如祖先设了 `pointer-events:none`）退回祖先链，让测量降级而不是消失。

**已知边界**：栈中位于 `el` **之上**的元素被忽略——「文字被别的元素盖住」是遮挡问题，本门禁不回答。

### D2 — 双档阈值，形状借 WCAG 的 large-text 宽限
`MIN_CONTRAST = 2.3`（正文）· `MIN_CONTRAST_LARGE = 1.8`（≥24px，或 ≥18.66px 且 bold）。

**阈值由实测标定，不由手算**：对四个内置 example 实测 Chrome 真正绘制的**每一个**文本元素（369 个），与缺陷值对照 ——

| 形态 | 实测 | 备注 |
|---|---|---|
| 缺陷（on-dark 浅字在浅卡片） | **1.10:1** | 28px h2，属 large |
| 合法 large 最低 | **2.57:1** | showcase 80px 橙色装饰数字压深青底 |
| 合法正文最低 | **3.12:1** | 14px accent kicker |
| 正确的 S04 栏头 | 9.96:1 | |

两档各自比「例子里合法的最低值」低约 1.4x，缺陷比 large 档还低 1.6x —— **两侧都不在刀刃上**。注意 discussions/052 §2.1 手算表预测的合法最低是 3.61，实测更低（2.57）；**若照抄手算表把阈值定在 2.3 单档，那个装饰数字就会被误杀** —— 实测这一步是必需的，不是仪式。

这是一条「人眼还看得见吗」的下界，**刻意远低于 WCAG AA 的 4.5** —— 门禁不该跟技能自己的 muted/accent 风格争论，只拦几乎不可见的。

### D3 — 判不了的不判，但**必须让人知道没判**
- 字色 `alpha == 0`（`background-clip:text` 渐变字一类的绘制技巧）→ 不测量。
- 绘制栈里有 `background-image`（含渐变）→ 合成出的背景不是真值，**照常测量并在 `--dump-contrast` 里标 `I`，但绝不据此判负**。宁可漏报，不可拿猜测拦人。
- **读不懂的颜色语法**（`oklch()` / `color()` / `lab()`——Chrome 的 computed 值会原样保留这些函数形式）**计数并在汇总行 + `NOTE:` 里明说**，同时写进 `qa_report.contrast.elements_unreadable_color`。首版是**静默跳过**，被自测抓到：那会让「0 low-contrast」可能实际等于「一个都没检查」——**这是门禁唯一绝不能有的失败模式**。deck 的 token 本就规定是 HEX，这里是防御性可见化而非支持。

### D4 — 与 overflow 同渠道，不新增门禁步骤
findings 走同一条命令、同一个 `qa_report.json`（新增 `contrast` 段，`overflow` 段结构不动）、同一个退出码（0 干净 / 1 有 finding）。门禁链仍是四步。新增 `--dump-contrast` 逐元素打印，供标定与排障。

### D5 — 引导同步硬化（便宜的补充，非替代）
`SKILL.md` Phase 5.2 明写「`--c-on-dark` 只能出现在 `data-dark` 页内，浅底标题/栏头用 `--c-primary`」；`visual-review.md` R4 补机器门禁指针，并把评审的职责收窄到「门禁放行范围内的观感」。

## 影响 / 风险

- 全部落在 `skills/builtin/deckcraft/`，**不碰 vendor patch、不碰业务 TS**；跨平台无新依赖（复用既有 Chrome 探针，Windows `CREATE_NO_WINDOW` 分支不变）。
- **误杀风险已由实测封顶**：四个内置 example 共 369 个文本元素全部放行。
- **前向生效**：老 deck 需重跑门禁链才受益。
- 新增 example / 换配色时若触到 2.3，应先看 `--dump-contrast` 判断是真缺陷还是调色板本身偏浅，**不要顺手调低阈值** —— 阈值的正当性来自上面那张实测表。
- **本门禁不回答的问题**（写明边界，免得后人误以为它覆盖了）：文字被上层元素**遮挡**、`::before/::after` 伪元素文字、图片/渐变底上的文字、读不懂的颜色语法（已计数播报）。
- 遗留（既有行为，非本 ADR 引入）：`probe_overflow.py` 每页 120s 的 Chrome 超时，在**连续大量启动** headless Chrome 时偶发触发。实测定位=测试套件一轮连开 ~40 个实例造成的资源争用；**单独探一份 deck 稳定（3/3）**，真实用法一次只探 7–14 页。故修测试脚手架（超时重试一次）而非放宽产品超时。

## 验证

`scripts/test-deckcraft-contrast.py` **45/45**：真实缺陷复现（实测 1.1:1，与 052 记录一致）· 同卡片正常正文/正确栏头/deliberate muted 全放行 · `data-dark` 页上同一个 on-dark 色判为正确（10.98:1，证明合成背景真的解析到了深底而非默认白）· **绝对定位兄弟色块上的浅字放行（12.92:1，背景正确解析为该色块而非祖先）** · 阈值边界 2.0 判负 / 2.6 / 3.0 放行 · large 宽限（同色 40px 放行、14px 判负，而缺陷 1.1 仍被逮住）· 透明字与图片底跳过 · **读不懂的颜色被计数并播报** · **注入 JS 的亮度算法与独立 Python 实现逐元素对账**（防两侧任一悄悄漂移）· `qa_report` 写入与退出码 · 四个内置 example 零误报 exit 0。

算法从祖先链改成绘制栈后**重新标定**：四例仍是 369 个元素，逐元素比对（比值 + 前景 + 背景）**与旧算法完全一致**，最低值仍是 large 2.57 / 正文 3.12 —— 阈值依据未移动。

`deckcraft-selftest.py` 48/0 无回归 · `test-deckcraft-validate.py` 26/26。**客户机安装模拟**：把 `skills-builtin.zip` 解压到与仓库无关的目录，从解压位置对拷贝出去的项目运行 probe（相对路径 / `cwd=/` 绝对路径两种调用）均正常 —— 零仓库相对假设。zip 含新 probe、**不含**开发测试脚本。

### 通用性（不是只对那四个样例成立）
样例全是浅底为主，而**调色板由模型每份 deck 现场生成**（`design-styles/*` 只给定性指导、不给固定 HEX），所以「在我们的样例上没误报」不是要证明的命题。补了 `tech-dark`（整份深底）调色板实测并固化为回归用例：正确元素**最弱 7.24:1**、零误报；**深底上用同色系深色（`--c-primary` on `--c-bg`）被逮住 1.37:1** —— 那正是原缺陷的镜像形态（浅底上用浅字）。说明门禁判的是「前景与实际背景的关系」，不是「某个 token 名字」，明暗两端都成立。

同时确认一条**设计边界而非漏检**：深底上误用浅底方案的暗 muted（`#5A6B7B`，风格文档明令禁止）测得 3.38:1 **放行**——它虽违反风格指导但仍看得见，而本门禁的阈值刻意远低于 WCAG AA，只拦「几乎不可见」、不替风格指南执法。

### 真模型端到端（`deckcraft-fullpipeline-realmodel.e2e.ts`，两轮）
用真 qwen 从一句「做PPT」跑完整管线（技能加载 → 两轮 question → outline → 门禁链 → 逐页生成 → deck.html），抽取的正是打包后的 zip（含本次 probe）：**两轮均 PASS，新门禁未在真实流程中造成卡死或返工循环**；日志可见模型被问到 **消费距离（`delivery_purpose`）**，ADR-066 的新问题轮在真模型下生效。

第二轮保留了产物，对**模型亲手生成、非样例、非人工编写**的 deck 跑对比度门禁：模型**自选了一套深色调色板**（`--c-bg:#0F172A` / `--c-text:#E2E8F0` / `--c-muted:#94A3B8`，HEX 与四个样例及合成测试全不同），**75 个文本元素 0 误报、0 不可读颜色、exit 0**，最弱合法元素 4.46:1（页码）距 2.3 下界余量充足。这是比任何合成用例都强的通用性证据 —— 阈值不是对着我们的样例调出来的。

### 性能（无衰退）
在页面内直接计时 `measure()`（避开 Chrome 启动噪声），对 10 页样例 A/B：**仅溢出 11.6 ms/页 → 溢出+对比度 17.3 ms/页，增量 +5.7 ms/页**，相对每页 Chrome 启动渲染（~1500 ms）为 **0.38%**。命中测试（`elementsFromPoint`）按可见文本元素调用，量级与页面元素数同阶，无病态放大。

### JS↔Python 对账的口径（首版对账口径有误，已修正）
被判定的是**全精度合成值**，而 `--dump-contrast` 打印的 hex 是它的 8-bit 舍入。对不透明前景两者等价；对 alpha 合成的前景（如 `rgb(20 20 20 / 90%)` 落在通道 43.5）半个量化级会让比值差约 1%。首版对账用「精确值 vs 从 hex 反算」严格比 0.02，误报为算法漂移 —— **判定本身是对的（14.06），错的是对账口径**。现改为相对容差 1%（含 0.02 绝对下限），并另加一条断言锁「不透明前景必须仍在 0.02 内吻合」，否则那才是真的数学 bug。
