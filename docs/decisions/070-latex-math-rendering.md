# ADR-070：数学公式（LaTeX）渲染 —— 裸装 remark-math + rehype-katex，零启发式

- 状态：已接受（P1 + P2 **均已真机验收通过**，2026-07-27）
- 日期：2026-07-27
- 相关：discussions/055（完整调研与四轮方案演进）· ADR-064（`rich-output.ts` 系统提示注入点）· ADR-050 / discussions/033（IM 出站净化）· gotchas §18 · conventions §19

## 背景

用户提供两张真机截图对比（同一问题「拒绝采样是指?」、同一模型 qwen3.7-max）：对照产品把公式渲染成数学排版，本项目**原样吐出美元符号源码**。

根因四层，全部实测（用项目实际在用的 `react-markdown@9.1.0` + `remark-gfm@4.0.1` 复现，非读码推断）：

1. **管线里没有任何数学插件** —— `message-parts.tsx` 的插件数组只有 `[remarkGfm]`，全仓 grep `latex|katex|mathjax` 在产品代码零命中。
2. **降级后连「原样显示」都做不到** —— `$\frac{p(x^*)}{M \cdot q(x^*)}$` 的两个 `*` 被 GFM 配对成 `<em>`，星号消失、斜体下的 `\` 看着像 `|`，与截图逐字符吻合。另一类是 `\{ \_ \%` 被 CommonMark 转义吞掉，而 `\cdot`/`\frac` 不受影响（`c`/`f` 非可转义标点）⇒ **损伤是选择性的**。
3. **`\(...\)` 在解析期即被销毁** ⇒ 任何修复必须发生在 markdown 解析之前或之内，渲染后 DOM 补救不可能。
4. **prompt 从未约定公式格式** —— `rich-output.ts` 的 `<output_format>` 规定了图片语法却一字未提公式。

## 决策

### D1：裸装 `remark-math`（默认配置）+ `rehype-katex`，不写任何启发式

`singleDollarTextMath` **保持默认 `true`**（接受单 `$`），`throwOnError:false` + `strict:false`。落在 `message-parts.tsx`（聊天）与 `artifact-preview.tsx`（`.md` 产物预览）两处 —— 全仓仅这两处 `<ReactMarkdown>`。

**这是三次自我推翻后的结论，前三版都更复杂且更差**（详见 discussions/055 §十）：

| 版本 | 方案 | 被什么推翻 |
|---|---|---|
| 初版 | 保留单 `$` + mdast 层货币守卫 | micromark 贪婪配对会偷走真公式的定界符，mdast 层已太晚 |
| 二版 | 保留单 `$` + 分词前字符串守卫 | 第一版实现即误杀真公式并向界面漏出 `\5` 脏字符 |
| 三版 | `singleDollarTextMath:false` + prompt 引导 `$$` + 白名单救援 | P0 实测引导只到 82.4%、混用 4/12 ⇒ 把模型智力变成单点依赖 |
| **定稿** | **裸装，零启发式** | 真实语料实测 **279 个公式零误伤** ⇒ 三版赖以成立的前提本身不成立 |

关键取舍是**失败模式的方向**，以及一个被数据推翻的假设：

- 前三版都在防御「货币误伤」（`$5 … $10` 配成公式），而该风险**从未用真实语料验证过**。拿 P0 产出的 **24 个真实模型回答 / 279 个公式**跑裸装管线：**真实误伤 0**（4 个疑似经复核全是真公式）。
- 为防御它而关掉单 `$`，代价是把渲染正确性绑死在模型行为上 —— 实测 qwen3.7-max **85% 的公式用单 `$`**，prompt 明确要求 `$$` 也只到 82.4%，且 **4/12 的回答混用两种定界符**（同一条回答一半渲染一半不渲染，观感比全不渲染更差）。

⇒ **副作用的严重性必须先用真实语料量化，再决定为它付多少复杂度**，否则防御本身成为更大的风险源。

### D2：KaTeX 而非 MathJax；`\(...\)` 不支持

KaTeX 自带字体、跨端确定性一致（项目要求三平台一致，ADR-037）；MathJax 的体积/性能优势不存在，且**换渲染器救不了 `\(...\)`** —— 定界符由 `remark-math` 的**分词层**决定，不在渲染层。`\(` 因根因 3 无解，只能靠 prompt 劝阻（qwen 实测 0 次使用，GPT 系有此习惯）。

### D3：修 IM 出站的公式篡改（独立既存缺陷，一并做）

`wechat-adapter.ts` 的 `stripMarkdown` 用裸正则剥离强调，`_(.+?)_` **跨公式配对**，把 `$\sum_{i=1}^{n} a_i = b_i$` 发成 `$\sum{i=1}^{n} ai = b_i$` —— 求和下标丢失、`a_i` 变 `ai`，**数学含义在出站前被改变**。

与根因 2 同源，但**桌面端有 CommonMark 的 intraword 保护、IM 端的裸正则没有** ⇒ IM 端更严重：桌面端只是显示难看，IM 端是内容错误。修法是公式区段先占位、剥离强调后再还原。**该缺陷独立于本 ADR 存在，本来就该修。**

### D4：两条 CSS 兜底 KaTeX 自身的缺口

- `.katex-display{overflow-x:auto}` —— KaTeX 带 `white-space:nowrap` 却不带任何 overflow 规则，超宽块级公式会撑破正文列或被裁（而修复前的源码形态会折行、内容全可见）。**副作用是好的**：公式外部宽度被锁在列宽内，顺带消除了流式期间的横向抖动。
- `.katex-mathml{user-select:none}` —— KaTeX 把公式输出三份（MathML + `<annotation>` 原文 + 可视 HTML），拖蓝选中会复制到三重重复。用 `user-select` 而非 `display:none`，MathML 要留在无障碍树里。「复制整条回答」按钮不受影响（走 `answerText` 原文）。

### D5（P2，2026-07-27）：IM 出站 LaTeX→Unicode 降级，落在 `bridge.ts` 一处，用 KaTeX 解析器

D3 只做到「不篡改」，公式仍以源码形态到达 IM 用户。P2 把它降级成 Unicode：`$M \cdot q(x) \geq p(x)$` → `M⋅q(x)≥p(x)`。

- **落点是 `bridge.ts` 的 `send()`**，不是四个 adapter —— 那是所有出站消息的唯一漏斗（streamed block 与最终 flush 都过它），沿用 discussions/033 P0「净化全在 bridge.ts 一个文件」的既有做法。四家（微信纯文本 / 钉钉·企微 markdown / 飞书 text）无一渲染 LaTeX，没有需要区分对待的通道。
- **转换由 KaTeX 的解析器做，不是正则**：`katex.__renderToDomTree(tex, {output:"mathml"})` 返回 MathML **树对象**，省掉解析 XML 字符串这一步。P1 期间手写的两版 `$` 守卫**各自出过一次错**（一版误杀真公式、一版往界面漏 `\5`），这是不再用正则做语义判断的直接原因；正则在此只负责**定界符扫描**，且刻意与桌面 remark-math 的 `$…$` / `$$…$$` 保持一致。
- **朴素取树文本不够**：MathML 平铺分子分母，`\frac{1}{M}` 的朴素文本是 `1M`（一个不同的数）⇒ `mfrac / msup / msub / msubsup / munderover / mover / munder / msqrt / mroot / mtable` 全部规则处理，`<annotation>`（LaTeX 原文）显式丢弃。
- **失败即保留原文**：KaTeX 解析失败或结果为空 → 原样送出，等于今天的行为。这让 P2 在最坏情况下不劣于 P1。
- **括号策略：分母看树，分子看字符串**。字符串层的「顶层运算符扫描」对并置乘法失明（`\frac{1}{2\pi}` 的分母里没有运算符字符，会输出读作 `(1/2)·π` 的 `1/2π`），故分母的原子性由**节点**判定（单原子 / 已被括号包住 / 函数调用 `Q(i)` 三种放行）。
- **跳过 code 与 URL**。实测桌面管线**保留** `[文档](https://ex.com/a$b$c)` 与裸 URL 里的 `$`，IM 侧照转会把 URL 静默改成 `.../abc` —— 那是桌面端没有、IM 端独有的损坏，不是可以接受的「两端一致」。code 同理（`$PATH … $HOME` 会被当成一个 span 吞掉）。
- **顺带修 `stripMarkdown` 的 `_` 规则**：降级产物里 `_(…)` 是常客（Unicode 映射不了的下标），两处会被裸 `_(.+?)_` 配成一对。补上 CommonMark 的 intraword 保护 —— 桌面端白拿的那条。
- **KaTeX 不是「成功或抛异常」二选一**：它认识但被 `trust` 门控的命令（`\href` / `\url` / `\includegraphics`）**不抛**，而是把命令名按 `errorColor` 上色渲染 —— `\href{...}{点我}` 出来只有 `\href`，**「点我」静默消失**。故把 `errorColor` 设成哨兵色、树里遇到即当解析失败保留原文。**不能靠扫输出里的反斜杠判断**：`a \backslash b` 合法地渲染成 `a\b`。
- **唯一无法走漏斗的出站点已显式处理**：答案格式错误时的重新追问必须回复**那条入站消息**（adapter 的 `reply` 绑定在具体消息上），不能用 `send()` 的本回合原始 reply（群聊会回错上下文）⇒ 该处显式调一次降级，否则同一个问题第一次是降级的、重问时变回源码。
- **刻意不做**：货币白名单（决策依据见 discussions/055 §13.5 的双向量化）· `\(...\)`（根因 3，解析期即失效）· 为钉钉/企微写方言分支（其渲染行为本就未实测，见「已知残留」）。

## 后果

**正面**：截图里的全部失败案例修复；顺带消除根因 2 的源码破坏；顺带修掉 IM 侧一个内容篡改缺陷；对模型行为零依赖，换模型不影响正确性。

**这不是纯加法** —— 四处体验衰退（discussions/055 §七之前）：W1 长公式横向溢出（已用 CSS 处置）· W2 流式抖动（实测块级公式宽度 0 次变化、高度 3 次，温和）· W3 局部选中复制丢失 LaTeX 源码（不可避免，对照产品同样）· W4 非法公式由源码变红字（可接受）。

**P2 正面**：IM 用户看到的从源码变成可读排版；四家一次受益；对模型行为同样零依赖。

**P2 代价**：IM 端拿不到 LaTeX 源码（可读性优先于可复制性，D5 的取舍）· 降级是**有损近似** —— `\mathbb{R}` 退成 `R`、`\mathbf{v}` 退成 `v`（丢失字体变体语义）、`\begin{cases}` 只有左花括号故输出看着不配对（忠实于 LaTeX 语义但观感怪）· 部分表达式比人手写的多一层括号（`∂f/(∂x)`，安全方向）。

**成本**：桌面包体积 +~590KB（katex.min.js 272KB + CSS 24KB + woff2 296KB，未压缩）；流式每帧 +1.6ms（最坏 42 公式样本，0.75→2.35ms，远在 60fps 的 16.7ms 预算内）；gateway sidecar **+468KB**（实测 65,297,280 → 65,776,128 字节，比预估的 272KB 大）。

**已知残留**：英文/金融语境的货币误伤未测（P0 语料全中文数学题）· 字体打包了 woff/ttf 冗余 876KB（三平台 WebView 全支持 woff2，可选优化）· 超宽公式被裁时无「可横向滚动」的视觉提示（罕见，实测真实语料不触发）· 真机只覆盖 macOS 版钉钉/企微客户端，Windows/Android 版渲染器理论上可能不同（同源代码可能性大）。

### P2 对抗性复核（真机验收前，2026-07-27，详见 discussions/055 §十三）

- **补真端到端 e2e** `e2e/im-math-degrade.e2e.ts`（`e2e:im-math`，14 项断言）：mock-llm-math → 真 opencode → 真 Bridge（真 SSE + 真 BlockChunker + 真 `send()`）→ 抓出站文本。**与桌面 `e2e:math-real` 共用同一份 mock 回答**，两者构成同一输入的真 A/B。首次「四家渠道拿到逐字节相同文本」得到实证 —— 那正是把代码放 `send()` 而非四个 adapter 的理由。
- **两个缺陷是这一轮抓出来的、单测抓不到**：① `\href` 静默吞内容（见 D5 第 8 条）；② 重新追问绕过降级漏斗（见 D5 第 9 条）。
- **对抗性探测**：20k 上限下 8 种病态输入最慢 22ms 无 ReDoS · 宏炸弹被 KaTeX `maxExpand` 拦下并保留原文 · 300 组随机输入 0 个非幂等 · 1000 个无 `$` 串 0 个被改动 · CRLF 与 LF 行为一致。
- **「`$` 歧义」从推断变实测**：6 个 shell/路径场景在**桌面端管线**上全部已被当公式渲染、损坏形态逐字相同 ⇒ P2 是**继承**已发版的取舍，不是新增 IM 独有损坏（判据同 URL 那条 —— URL 桌面端不损坏，所以必须修）。在本仓库 225 个 md / 2.45M 字符真实技术中文文档上，误转换 **3 处**（≈1.2/百万字符）；反向代价是白名单方案会漏掉 **29.4%** 的真实公式。两侧数据都在 discussions/055 §13.5，供将来反悔时用。
- **跨平台/打包实证**：`math-unicode.ts` 只 import `katex`，零 node 内置 / 零路径 / 零 `process.env` ⇒ 构造上三平台一致。编译产物里 katex **完全内联**（把 `node_modules/katex` 物理移走后二进制仍正常工作），无运行时解析、无 P2 相关的绝对路径；`stripMarkdown` 的 lookbehind + `\p{L}` 在 `bun build --compile` 产物中实测可用。
- **黑盒验证编译产物** `e2e/im-math-sidecar-blackbox.e2e.ts`（`e2e:im-math-blackbox`，13 项断言）：mock ilink 服务器 → **编译后的 sidecar 二进制**（真 ChannelManager + 真微信 adapter + Bridge + `stripMarkdown`）→ 真 opencode，断言打在它真实 POST 出去的 HTTP 报文上。锁住三件源码级测试锁不住的事：`\p{L}`+lookbehind 在 `bun build --compile` 产物中生效 · 降级早于 `stripMarkdown` 拆围栏的**顺序保证**（`$PATH` 因此存活）· 回答被切成 3 条 IM 消息后拼接仍完整。
- ~~唯一未闭合项~~ **已真机验收关闭**（discussions/055 §十四）：钉钉与企微**都遵守 CommonMark 的 intraword 规则**，同一行两个 `_` 的决定性用例（`D_(KL)(P∥Q)≠D_(KL)(Q∥P)`）在两家均完好，Unicode 下标/`∥`/`∈` 字形也全部正常 ⇒ A 案（下标括号）与 B 案（按渠道转义）都不需要做。真机同时验证了**真实模型输出**上的降级正确性 —— 模型自发写出的 `\mathrm` / `\mathcal` / `\parallel` / `\neq` 在所有 mock 用例里都没出现过。
- **方法论教训**：中途曾据用户粘回的文本误判「企微把 `_` 配对了」，截图证明是**粘贴链路**吃掉了同一行的那对下划线。**验证 markdown 行为时粘贴文本不是证据 —— 它经过了另一个渲染器**，必须截图或与发送端字节对照。
