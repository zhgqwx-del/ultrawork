## 一、现象

同一个问题「拒绝采样是指?」，同一个模型（qwen3.7-max）：

| | 对照产品 | 本项目 |
|---|---|---|
| `$M \cdot q(x) \geq p(x)$` | 渲染为居中数学排版 | 原样显示美元符号源码 |
| 表格内 `$\frac{1}{M}$` | 渲染为分式 | 原样显示 |
| `$\frac{p(x^*)}{M \cdot q(x^*)}$` | 渲染为分式 | 显示成 `$\frac{p(x^)}{M |cdot q(x^)}$`（**星号丢失、反斜杠被斜体化得像竖线**） |

最后一行说明问题不止「没渲染」一层 —— 降级后连「原样显示」都没做到。

---

## 二、根因（四层，全部有实测证据）

复现环境：项目**实际在用**的依赖（`packages/client/desktop/node_modules` 下的 `react-markdown@9.1.0` + `remark-gfm@4.0.1`），非另装新版本。

### 2.1 根因 1（主因）：渲染管线里没有任何数学插件

`packages/client/desktop/src/components/chat/message-parts.tsx:67`：

```ts
const REMARK_PLUGINS = [remarkGfm]   // 全部插件就这一个
```

`package.json` 无 `remark-math` / `rehype-katex` / `katex` / MathJax 任何一个；全仓 grep `latex|katex|mathjax` 在产品代码零命中（仅 markdown-exporter skill 的 `md_to_latex`，无关）。⇒ `$...$` 只是普通文本。

### 2.2 根因 2：markdown 内联规则会二次破坏公式源码

```
SRC : 以概率 $\frac{p(x^*)}{M \cdot q(x^*)}$ **接受**该样本
HTML: 以概率 $\frac{p(x^<em>)}{M \cdot q(x^</em>)}$ <strong>接受</strong>该样本
```

两个 `*` 被 GFM 当强调符号配对消费 → `<em>`，星号消失；斜体字形下的 `\` 看着像 `|`。**与截图逐字符对上**。

第二种损伤是反斜杠转义：

```
SRC : $\{x \| x > 0\}$ and $a \_ b$ and $50\%$
HTML: ${x | x > 0}$ and $a _ b$ and $50%$        ← 反斜杠全被吞
```

`\{ \} \_ \% \& \$` 在 LaTeX 里都是合法转义，撞上 CommonMark 转义规则即被吞；而 `\cdot`/`\frac`/`\sum` 不受影响（`c`/`f`/`s` 非可转义标点）⇒ **损伤是选择性的，更难排查**。

> **一个被实测推翻的假设**：原以为下标 `_` 也会被破坏。实测 `$x_0$`、`$\sum_{i=1}^{n} a_i = b_i$` 在**桌面端**完好 —— CommonMark 的 intraword 强调禁用规则挡住了。**不要把它当桌面端问题治**。（但 IM 端会坏，见 §4.1 —— 那里用的是裸正则，没有这条保护。）

### 2.3 根因 3：`\(...\)` / `\[...\]` 定界符在解析阶段即被销毁

```
SRC : 行内 \(a^2+b^2=c^2\) 与行间 \[E = mc^2\]
HTML: 行内 (a^2+b^2=c^2) 与行间 [E = mc^2]      ← 定界符信息已彻底丢失
```

**这条决定了架构约束**：任何修复必须发生在 markdown 解析之前或之内，**不能在渲染后的 DOM 上补**。也是否掉「正则后处理」类方案的硬理由。

### 2.4 根因 4（上游侧）：prompt 从未约定公式格式

`vendor/opencode/src/plugin/rich-output.ts` 的 `<output_format>` 明确告知模型「输出渲染为 GFM」，还专门规定了图片语法，**唯独一字未提数学公式** ⇒ 模型在 `$` / `$$` / `\(` 之间自由裁量。这既是「定界符五花八门」的来源，也是本方案最便宜的抓手。

## 三、候选方案实测对比

隔离沙箱（`scratchpad/mathbox`，不碰项目依赖），装 `remark-math@6` + `rehype-katex@7` + `katex@0.18`，并把 `react-markdown` 钉到项目在用的 `9.1.0`。

### 3.1 裸装 remark-math（保留单 `$`）：修好了主诉，但引入两个新回归

| 用例 | 结果 |
|---|---|
| `$q(x)$`、`$M \cdot q(x) \geq p(x)$`、`$$...$$`、表格内公式 | ✅ 全部正确渲染 |
| `$\frac{p(x^*)}{M \cdot q(x^*)}$` | ✅ **星号问题一并消失**（math 在 micromark 层先于强调规则夺取 `$...$`） |
| 代码块 / 行内 code 里的 `$` | ✅ 不受影响 |
| 非法 LaTeX（`throwOnError:false`） | ✅ 降级为红字，不崩 |
| `It costs $5 today and $10` | ❌ **误伤**：`$5 today and $` 被渲染成公式 |
| `价格 $5 和 $10` | ❌ 中文同样中招 |
| 流式半截 `$$\nM \cdot q(x)`（未闭合） | ⚠️ **立即渲染** ⇒ 流式期间公式抖动重排 |
| `\(...\)` `\[...\]` | ❌ 仍不支持（remark-math 只认 `$`，且反斜杠已被吞） |

### 3.2 被推翻的假设 A：mdast 层货币守卫

思路：让 remark-math 正常分词，再用 remark 插件遍历 `inlineMath` 节点，把「像货币」的降级回 text。

```
货币 en / 货币 cjk      → ✅ 0 公式，原文完整还原
代码块 / 行内 code      → ✅ 天然免疫（本就不产生 math 节点）
★ 成本 $100 时，接受率为 $\frac{1}{M}$。  → ❌ 0 公式，真公式没渲染出来
```

**失败原因**：micromark 从左到右贪婪配对，`$100 时，接受率为 $` 先被配成一个公式，守卫把它降级还原后，**后面真公式的开定界符已经被偷走了**。⇒ 损伤发生在分词阶段，**mdast 层已经太晚**。

### 3.3 被推翻的假设 B：分词前的字符串预处理守卫

思路：在交给 markdown 之前，把「像货币」的 `$` 转义成 `\$`，并跳过代码围栏 / 行内 code。

```
货币 en / cjk           → ✅ 0 误伤
★ 混排 货币+公式         → ✅ 治好了（3.2 治不了的，这里治住了）
代码围栏 / 行内 code     → ✅ 正确跳过
解为 $2x + 1$ 与 $5$    → ❌ 真公式被误杀，界面漏出垃圾字符 "\5"
```

**结论**：思路可行，但要同时跟踪代码围栏、行内 code、贪婪配对边界，**第一版实现即出错，且出错方式是往用户界面吐脏字符**。这类手写 `$` 配对守卫的期望缺陷率不可接受。

### 3.4 选定：`singleDollarTextMath: false`（只认 `$$`）

| 用例 | 结果 |
|---|---|
| 行内 `$$q(x)$$` | ✅ 渲染为 inline math |
| 块级 `$$` 独占行 | ✅ 仍是 display math |
| 货币 `$5 … $10 … $5,000` | ✅ **零误伤**（结构性消除，非启发式） |
| 混排 `成本 $100 时，接受率为 $$\frac{1}{M}$$` | ✅ 正确 |
| 表格内 `$$\frac{1}{M}$$` | ✅ |
| 模型不听话仍用单 `$` | ⚠️ 不渲染，降级为原文（= 今天的状态，不倒退） |

**选它的决定性理由是失败模式的方向**：

| 方案 | 失败时会发生什么 |
|---|---|
| 只认 `$$` | 公式**没渲染**，原样显示 —— 就是今天的状态，不倒退 |
| 保留单 `$` | 正常英文被渲染成斜体数学、真公式被偷定界符、脏字符漏到界面 —— **比今天更糟** |

补充理由见 §4.3（IM 侧带来的第二个独立理由）。

## 四、IM 渠道（用户明确要求「尽量适配，至少不衰退」）

### 4.1 新发现：IM 端今天已经在**篡改**公式（既存缺陷，此前未记录）

`packages/channel/gateway/src/adapters/wechat/wechat-adapter.ts:301` 的 `stripMarkdown` 用裸正则剥离强调，实测：

```
$\sum_{i=1}^{n} a_i = b_i$   →   $\sum{i=1}^{n} ai = b_i$
```

`_(.+?)_` **跨公式配对**，吃掉了求和下标、把 `a_i` 变成 `ai` —— **数学含义被改变**。桌面端只是显示难看，IM 端是内容被改写。

同源损伤：`$\frac{p(x^*)}{M \cdot q(x^*)}$` → 星号丢失（`\*(.+?)\*` 所致）。

> 与根因 2 同源（`*`/`_` 被当强调消费），但**桌面端有 CommonMark 的 intraword 保护、IM 端的裸正则没有** ⇒ IM 端更严重。**这个缺陷独立于本方案存在，本来就该修。**

### 4.2 四家出站格式（源码核实）

| 渠道 | 发送格式 | LaTeX 现状 |
|---|---|---|
| 微信 iLink | `stripMarkdown` → 纯文本 | **已实测受损**（§4.1） |
| 钉钉 | `msgtype: "markdown"`（`dingtalk-adapter.ts:202`） | ⚠️ **推断**受损（其 markdown 渲染器应同样消费 `*`/`_`），**未真机实测** |
| 企微 | `msgtype: "markdown"`（`wecom-adapter.ts:183`） | ⚠️ 同上，**未真机实测** |
| 飞书 | `msg_type: "text"`（`feishu-adapter.ts:171`） | 原样发 markdown 源码，不经 `stripMarkdown` ⇒ LaTeX 原文完整，但用户看到的是源码 |

### 4.3 `$$` 定界符对 IM 是净收益，不是代价（实测）

```
$$M \cdot q(x) \geq p(x)$$   →   原样无损穿过 stripMarkdown
$\sum_{i=1}^{n} a_i = b_i$   →   被改写（§4.1）
```

⇒ 统一 `$$` **同时改善** IM 端，不存在「桌面受益、IM 衰退」的取舍。

**这还给了 §3.4 第二个独立理由**：单 `$` 的货币歧义成本要在**每一个消费端各付一遍**（桌面 + 4 个 adapter，每处都要写一套 §3.3 已证明易错的启发式）；`$$` 是一次性消除歧义，下游全部受益。

### 4.4 「尽量适配」的上限：LaTeX → Unicode 降级（原型已验证）

复用即将引入的 KaTeX 解析器（**不是正则**，正确性由解析器保证），60 行原型实测：

```
$M \cdot q(x) \geq p(x)$        →  M⋅q(x)≥p(x)
$x_0$                           →  x₀
$\sqrt{x^2 + y^2}$              →  √(x²+y²)
$\int_0^1 f(x) dx$              →  ∫₀¹f(x)dx
$\alpha + \beta \leq \gamma$    →  α+β≤γ
$\frac{1}{M}$                   →  (1)/(M)          ← 括号冗余，可优化
$\sum_{i=1}^{n} a_i = b_i$      →  ∑_i=1ⁿaᵢ=bᵢ      ← 混合下标回退，仍可读
$\notacommand{x}$               →  ⟨解析失败 → 保留原文⟩   ← 安全失败
```

实现要点：`mfrac` / `msup` / `msub` / `msubsup` / `msqrt` 需规则处理，否则 MathML 朴素取文本会把分式拍平成 `1M`（错误）。

落点应在 **`bridge.ts` 公共层**（沿用 discussions/033 P0「净化全在 bridge.ts 一个文件」的既有做法），而非四个 adapter 各写一遍。

## 七之前：这不是「纯加法」—— 四个真实的体验衰退点

方案的**主轴**是纯加法（今天不渲染的公式变成渲染，其余不变），但「渲染」这个动作本身会替换掉今天的原文形态，因此存在四处**今天更好、明天更差**的地方。它们不阻塞方案，但必须在 P1 一并处理，否则真机会翻车。

| # | 衰退 | 今天 | 加库之后 | 处置 |
|---|---|---|---|---|
| **W1** | **长公式横向溢出 / 被裁** | 源码文本正常折行，**内容完整可见** | KaTeX `.katex-display>.katex{white-space:nowrap}` **强制不换行**，且其 CSS 唯一的 overflow 声明是 `overflow:hidden` ⇒ 长公式（KL 散度、交叉熵那类）在聊天区宽度内撑破布局或被裁掉右半边 | **P1 必做**：`.katex-display{overflow-x:auto}`；`chat-md` 容器同步检查 |
| **W2** | **流式抖动** | 文本平稳增长 | 块级 `$$` **半开即渲染**（实测），公式随 token 到达逐字重排跳动。行内单 `$` 半开不渲染（实测），故只影响块级 | P1 真机观察；必要时对未闭合 `$$` 延迟渲染 |
| **W3** | **局部选中复制丢失 LaTeX 源码** | 拖蓝选中 `$q(x)$` 复制得到**原始 LaTeX**，可粘贴到别处继续用 | 复制得到渲染后的 Unicode（`q(x)`），**源码丢失**；不加 CSS 还会得到三重重复 | CSS 压 `.katex-mathml` 的 `user-select` 治重复；**源码丢失不可避免**（对照产品同样如此），「复制整条」按钮走 `answerText` 不受影响 |
| **W4** | **非法 LaTeX 变红字** | 显示源码（难看但中性） | 显示**红色**错误块（内容仍是原文，仅着色 + title 带错误信息） | 可接受；`throwOnError:false` 已确保不崩 |

> W1 是本轮复盘新发现的，此前四轮讨论都没提到 —— 它恰恰是最可能在真机第一眼就暴露的那个。

## 八、未验项与风险

### 8.1 ✅ 模型听话率 —— P0 已实测（2026-07-27）

**方法**：直连 `alibaba-cn` / **qwen3.7-max**（项目 `opencode.json` 的默认模型），A/B 各 12 道数学题。system prompt 用**完整真实**组合（`default.txt` + `VERBOSITY_OVERRIDE` + `BRAND_GUIDANCE`，逐字从 `rich-output.ts` 提取），组 B 额外追加候选 `<math_format>` 段。用完整版而非简化版，因为简化会**高估**指令效果（真实场景里这条指令要与上百行其他指令竞争注意力）。脚本与全文存档见 `scratchpad/p0/`。

| | 公式总数 | `$$` | 单 `$` | `\(` | `\[` | **`$$` 占比** | 全用 `$$` 的回答 | **混用定界符的回答** |
|---|---|---|---|---|---|---|---|---|
| **A 现状**（无公式规定） | 120 | 18 | 102 | 0 | 0 | **15.0%** | 3/12 | **8/12** |
| **B 加引导** | 159 | 131 | 28 | 0 | 0 | **82.4%** | 8/12 | **4/12** |

**结论：引导有效但不充分 —— 单靠 prompt 的方案不成立。**

**三条关键发现**：

1. **组 A 坐实根因 4**：首题「拒绝采样是指?」产出 **22 个公式全部用单 `$`、零 `$$`** —— 与用户截图逐条对应。现状下 85% 的公式用单 `$`。

2. **失败是系统性的、有强规律的，不是随机的**：组 B 漏网的 28 个单 `$` **全部是行内短公式**，块级/长公式 100% 用对了 `$$`。样本：`$\mu$`、`$\sigma^2$`、`$x = \mu$`、`$\frac{1}{\sigma\sqrt{2\pi}}$`、`$\lambda_1 = 3$`、`$A = P\Lambda P^{-1}$`、`$d_k$`、`$P$`。⇒ 模型把 `$$` 理解成「块级公式」（LaTeX 普遍惯例），候选 prompt 里已明写 `for both inline and block formulas` 且给了行内例子，**仍抵不过这个先验**。继续加强措辞的边际收益存疑，且每次换模型/模型版本都要重测。

3. **漏网的单 `$` 里 75% 含 LaTeX 特征字符**（`\` `^` `_` `{}`）：组 B 28 个中 21 个含特征，剩余 7 个全是单字母变量（`$A$ $P$ $r$ $t$ $x$ $P = 1000$ $t = 10$`）。组 A 的 102 个中 69 个（67.6%）含特征 ⇒ **同一条规则对「模型不听话」和「存量文本」都有效**。

**⇒ 方案修正**：增加一条**不依赖模型**的白名单救援规则 —— 把「内容含强 LaTeX 特征的成对单 `$`」也当作公式渲染。判据是**正向白名单**（「含 LaTeX 特征」）而非负向黑名单（「像不像货币」）：前者失败=漏渲染（安全），后者失败=误渲染（§3.3 已证危险）。

**预估覆盖率**：82.4% + 17.6% × 75% ≈ **95.6%**。剩余 ~4.4% 是 `$A$`/`$P$`/`$r$` 这类单字母变量，不渲染的观感代价很小（多两个符号，不同于 `$\frac{p(x^*)}{M \cdot q(x^*)}$` 那种难看的破损）。

**附带发现（降低但未消除货币风险）**：24 个中文数学回答里**没有出现过一处真正的货币 `$` 写法** —— 连「本金 1000 元年利率 5%」那题，模型写的也是 `$P = 1000$` 和「1000元」，而非 `$1000`。（正则命中的 10 处经复核全是假阳性：`$\n2.` 是块级公式后的列表编号，`$7.39` 是 softmax 的计算结果。）⚠️ **不可外推**：样本全是中文数学题，英文 / 金融 / 电商语境的货币风险未测。

### 8.2 ✅ 真实语料实测：裸装管线的真实误伤 = 0 —— 推翻「必须让模型改用 `$$`」这个前提

**这一节推翻的是我自己在 §3.4 / §8.1 引入的前提，不是外部约束。**

§3.4 选 `singleDollarTextMath:false` 的唯一理由是「保留单 `$` 会有货币误伤」。但那个判断来自**我手编的用例**（`It costs $5 today and $10`），从未用真实语料检验过。而选了 `false` 就等于把「模型必须写 `$$`」变成硬依赖 —— 一个本可以不存在的单点风险。

**验证**：拿 P0 产出的 **24 个真实模型回答**（组 A + 组 B 全量）跑**裸装** `remark-parse + remark-gfm + remark-math`（默认配置，零启发式），统计所有 `inlineMath` / `math` 节点。

| 指标 | 值 |
|---|---|
| 行内公式 `inlineMath` | 262 |
| 块级公式 `math` | 17 |
| **合计成功识别** | **279** |
| 疑似误伤（保守判据） | 4 |
| **人工复核后的真实误伤** | **0** |

那 4 个「疑似」经复核全是真公式：中文变量名的贝叶斯公式 `P(患病|阳性) = \frac{...}`，以及三个 `\begin{pmatrix}` 矩阵 —— 是判据把 `pmatrix` 当成了自然语言词。

> **判据本身也翻过一次车**：第一版用 `\b[a-z]{3,}\b` 数自然语言词，把 `\cdot` / `\frac` / `\lambda` 全算了进去，报出 79 个假阳性。剥掉 `\command` 与 `\text{}` 后才降到 4。**"疑似误伤"这类指标必须先验证判据本身，否则会拿假阳性去否决正确方案。**

**边界渲染实测**（`throwOnError:false`）：中文变量名贝叶斯公式、`pmatrix` 矩阵、截图原句 `\frac{p(x^*)}{M \cdot q(x^*)}`、`\text{ 元}` —— **四者全部正常渲染**，无降级红字、无抛异常。⚠️ 中文变量名会触发 `strict:'warn'` 的 console 警告刷屏，实施时需设 `strict: false`。

**⇒ 定稿方案**：裸装，零启发式。

| | 原方案（`false` + 引导 + 救援） | **定稿方案（裸装）** |
|---|---|---|
| 对模型的依赖 | 硬依赖（P0 实测 82.4%，混用 4/12） | **零依赖** |
| 单 `$q(x)$` | 不渲染 | **渲染** |
| 需要写的启发式代码 | 白名单救援规则 | **无** |
| 真实语料误伤 | — | **0 / 279** |
| 性质 | 有取舍 | **纯加法**：今天不渲染的变渲染，其余不变 |

**保留为可选（不进 P1）**：① prompt 里劝阻 `\(...\)`（成本极低，`\(` 是唯一无解形态）；② 若真机出现货币误伤，再补保守降级规则（下节 §8.2.1 的实现 X）。

### 8.2.2 残留的模型相关风险：只剩 `\(...\)` 一处（未测）

定稿方案对模型行为零依赖 —— **但仅限于 `$` / `$$` 两种定界符**。`\(...\)` / `\[...\]` 因根因 3（反斜杠在解析期即被吞）无解，且换渲染器也救不了：**定界符由 `remark-math` 的分词层决定，不在 KaTeX/MathJax 的渲染层**，所以「改用 MathJax」不是解法。

- P0 实测：qwen3.7-max 两组共 24 个回答，`\(` 与 `\[` **出现次数均为 0** ⇒ 对当前默认模型风险为零。
- ⚠️ **未测**：GPT 系模型有使用 `\(...\)` 的习惯。若用户切换到该类模型，那部分公式会降级为 `(a^2+b^2=c^2)`（可读、不渲染，安全方向）。无实测数据，不做断言。
- 缓解：prompt 里一行劝阻（§九 第 4 条），成本极低。

### 8.2.1 若日后需要货币兜底：两种实现（当前不做）

| | 实现 X：mdast 层降级 | 实现 Y：分词前预处理升级 |
|---|---|---|
| 做法 | 开 `singleDollarTextMath:true`，在 mdast 上把**不含** LaTeX 特征的 `inlineMath` 降级回 text | 保持 `false`，解析前把「含特征的成对单 `$`」重写成 `$$` |
| 代码围栏 | ✅ **天然免疫**（fenced/inline code 本就不产生 math 节点，§3.2 已实测） | ❌ 需自行跟踪围栏 —— **§3.3 第一版实现即在此出错** |
| 货币+公式混排同段 | ❌ 真公式漏渲染（§3.2 实测；失败方向**安全**） | ✅ 正确 |
| 实现风险 | 低 | 中高 |

**倾向 X**：它免疫的正是 §3.3 栽跟头的地方，且失败方向安全。代价是 §3.2 那个混排场景仍漏渲染 —— 而 P0 数据显示该场景在中文数学问答里未出现。

### 8.2 🟡 钉钉 / 企微受损路径是**推断，非实测**

二者发 `msgtype: "markdown"`，其渲染器行为需真机发一条消息才能确认（§4.2）。

### 8.3 🟡 性能未量化

`assistant-turn.tsx:298` 每个 SSE delta 都把全量文本重新交给 ReactMarkdown。加 KaTeX 后，一个含 N 个公式的长回答在流式期间会触发 N × delta 次公式渲染。需实测长回答（含多公式）的流式 CPU 占用与掉帧。

### 8.4 已排除的风险

- **CSP**：`tauri.conf.json` 的 `"csp": null` ⇒ KaTeX 字体不会被拦（原先的头号疑虑，已排除）。
- **版本兼容**：沙箱用的就是项目在用的 `react-markdown@9.1.0` 配 `remark-math@6` + `rehype-katex@7`，实测跑通。
- **非法 LaTeX 崩溃**：`throwOnError:false` 降级红字，实测不崩。
- **代码块误伤**：实测 `$` 在 fenced code / inline code 内不受影响。

### 8.5 选型说明：KaTeX 而非原生 MathML

MathML 可省 272KB JS + 296KB 字体，但**三平台 WebView（WKWebView / WebView2 / WebKitGTK）的 MathML 渲染质量未经验证**，而项目要求三平台一致（ADR-037）。KaTeX 自带字体、跨端确定性一致。

- 高度变化 **3 次** —— 公式逐步成形，温和而非剧烈跳动
- 流式期间**任何采样时刻**都无 body / 聊天列横向溢出

> **同一个空转陷阱又踩了一次**：本测试首版跑出 `dispScrollW 812 == dispClientW 812` —— 812px 聊天列里那条 KL 散度公式（自然宽约 599px）**放得下**，于是 W1 的断言再次全部空转通过。加长公式到自然宽 925px 才真正触发。§11.1 已经栽过一次、**这里换个场景又栽了一次** ⇒ 布局类断言必须**逐场景**各配一条非空转自检，不能靠「上次验过了」。

### 11.6 截图暴露的新观感问题（W1 的处置遗留，需产品判断）

真实 app 截图显示：长公式在框内**右侧被直接切断**，没有任何视觉提示说明「这里可以横向滚动」。

- 技术上正确：`overflow-x:auto`，用鼠标/触控板可横向滚动，布局不被撑破。
- 但**发现性差**：macOS 默认是 overlay 滚动条（不滚动时不显示），用户可能误以为公式就到此为止 —— 而**修复前的源码形态是会折行、内容全部可见的**。

⇒ 这不是 bug，是 W1 处置方式带来的取舍。候选改进（未做，待定）：右侧渐变遮罩提示可滚动 · 超宽时自动缩小字号 · 常驻细滚动条。**建议交产品判断**。

## 十二、P2 实现记录：IM LaTeX→Unicode 降级（2026-07-27）

§4.4 的 60 行原型只验证了「能转」。真正实现时，**原型的输出有两处是错的**，而且都不是靠更仔细地想出来的 —— 是把真实语料灌进去才暴露的。

### 12.1 落点与结构

```
bridge.send()  ──►  degradeMathToUnicode(text)  ──►  MAX_REPLY_LENGTH 截断  ──►  adapter.reply()
                          │
                          ├── 扫描器：跳过 fenced code / inline code / 链接目标 / 裸 URL / <autolink>
                          └── 每个 $…$ / $$…$$  ──►  latexToUnicode()
                                                        └── katex.__renderToDomTree(output:"mathml")
                                                            └── 树 → 文本（规则处理 mfrac/msup/…）
                                                            失败 → null → 保留原文
```

- **一处落点**：`send()` 是所有出站消息的唯一漏斗，streamed block 与最终 flush 都过它 ⇒ 四个 adapter 一行不改（沿用 discussions/033 P0 的既有做法）。
- **先降级再截断**：截断在前有可能从一个 span 中间切开，留下半截不再可解析的 LaTeX。
- `__renderToDomTree(…, {output:"mathml"})` 返回的是 **MathML 树对象**，不是字符串 ⇒ 不需要解析 XML。这一点决定了「用解析器而非正则」不是口号：正则在整个模块里只剩定界符扫描一件事。

### 12.2 两个被真实语料抓出来的输出缺陷

用 P0 那 24 个真实模型回答（**279 个公式**）跑降级，人工过一遍输出：

| # | 输入 | 第一版输出 | 问题 | 定稿 |
|---|---|---|---|---|
| 1 | `\frac{e^{z_i}}{\sum_j e^{z_j}}` | `e^zᵢ/∑ⱼe^zⱼ` | 分母是**并置乘法**，没有任何运算符字符 ⇒ 字符串层的「顶层运算符扫描」完全看不见它，读作 `e^zᵢ/∑ⱼ · e^zⱼ` | `e^(zᵢ)/(∑ⱼe^(zⱼ))` |
| 2 | `y_{ic}\log(\hat{y}_{ic})` | `y_iclog(ŷ_ic)` | Unicode 没有下标 `c` ⇒ 整组回退成 ASCII `_`，而 `_`/`^` **没有闭合定界符**，下标到哪结束无从判断 | `y_(ic)log(ŷ_(ic))` |

第 1 条的修法是**把括号判据从字符串搬到树上**：分母只有三种形态可以裸奔 —— 单个原子、已被括号包住（`\left(…\right)`）、函数调用（`Q(i)`）。分子仍用字符串判据就够（`/` 比 `+`/`=` 结合更紧）。

第 2 条的修法是**回退形式永远带括号**，哪怕只有一个字符。顺带发现 accent 也是同类问题：KaTeX 发的是**间隔**重音符（`\hat{y}` → `y` + U+005E `^`），拼出来的 `y^` 和指数无法区分 ⇒ 映射到组合字符 U+0302 得 `ŷ`；`\underline` 发的是 `‾`（U+203E，**overline 字形**）要按 munder 方向映射到 U+0332。

> **这与 §十 的教训是同一条的两面**：那边是「别为想象出来的副作用付复杂度」，这边是「想象不出来的缺陷得靠真实语料抓」。手编用例（`\frac{1}{M}`、`\sqrt{x^2+y^2}`）全数通过，两个真缺陷一个没碰到。

### 12.3 一个必须跳过 URL 的理由（实测，不是推断）

扫描器最初只跳 code。用 `remark-parse + remark-gfm + remark-math` 实测桌面端行为：

```
见 [文档](https://ex.com/a$b$c) 说明   →  href = https://ex.com/a$b$c   （$ 保留，0 个 math 节点）
见 https://ex.com/a$b$c 说明          →  href = https://ex.com/a$b$c   （GFM autolink，同样保留）
```

⇒ remark-math **不碰链接目标**。IM 侧若照常转换，`$b$` 会被吃掉、URL 静默变成 `.../abc` —— 这是**桌面端没有、IM 端独有**的链接损坏，不能用「两端一致」辩护。故扫描器补上：`](…)` 目标、裸 `http(s)://…`、`<scheme:…>` autolink 三种形态。

### 12.4 顺带修：`stripMarkdown` 的 `_` 缺 intraword 保护

降级产物里 `_(…)` 是常客（Unicode 映射不了的下标）。裸 `_(.+?)_` 会把两处回退配成一对、吃掉中间正文 —— 与 §4.1 那个求和下标缺陷**同一个机制**，只是触发源从模型的 LaTeX 换成了我们自己的降级产物。补上 CommonMark 的 intraword 规则（`(?<![^\s])_ … _(?![\p{L}\p{N}])`），桌面端本来就白拿这条。

### 12.5 验证

| 项 | 结果 |
|---|---|
| 真实语料（P0 24 答 / 279 公式） | **279/279 转换成功 · 0 保留原文 · 输出 0 个残留 `\command`** |
| gateway 单测 | 260 → **290**（math-unicode 23 + bridge 4 + strip-markdown 3） |
| typecheck | 8/8 |
| desktop 单测 | 730（未动桌面代码，作对照） |
| e2e `math-css` / `math-real` | 全绿（Chromium；**桌面端零改动**，`git diff` 核查无 desktop 文件） |
| `bun build --compile` | katex 可打包；编译后二进制输出 `M⋅q(x)≥p(x)` 正确（按 gotchas §7 先 remove-signature 再 ad-hoc 签） |
| gateway sidecar | 重编译 + 实跑起停正常；体积 **+468KB**（65,297,280 → 65,776,128 字节，比预估的 272KB 大） |

### 12.6 已知限制（都不是缺陷，是取舍）

- **有损近似**：`\mathbb{R}`→`R`、`\mathbf{v}`→`v`（丢字体变体语义）；`\begin{cases}` 只有左花括号，输出 `{1 x>0; 0 x≤0}` 看着不配对（忠实于 LaTeX，观感怪）；部分表达式比人手写多一层括号（`∂f/(∂x)`，安全方向）。
- **钉钉/企微渲染器下的表现未真机实测** —— 与 §8.2 那条既有盲点同源。具体风险：产物里的 `_(…)` 若被对方渲染器当强调配对，可能吞掉中间正文。微信侧已由 12.4 覆盖。
- **`\(...\)` 在 IM 侧理论可行但刻意不做**：IM 收到的是原始文本、反斜杠还在，但支持它会让两端行为不一致。
- **货币误伤**：与桌面端同源、同判据（真实语料 0/279），不额外加白名单。差别在于 IM 侧此前是「原样发出」（正确），降级后会跟随桌面端一起把 `$5 和 $10` 渲染掉 —— 这是**为两端一致付的代价**，不是新增的独立风险。

## 十三、P2 的对抗性复核（2026-07-27，真机验收前）

§十二 交付后又做了一轮系统复核：补真端到端 e2e、对抗性探测、跨平台/打包核查。**又抓出两个缺陷，且都不是单测能发现的。**

### 13.1 补上缺失的那一段：IM 出站的真端到端 e2e

此前 P2 的验证是「单测调降级函数」+「真实语料跑函数」。两者都**没经过**一次真实回合：真 SSE 增量 → 真 `BlockChunker` 分块 → 真 `send()`。每一处都可能把公式切开、重排或重复降级。

补 `e2e/im-math-degrade.e2e.ts`（`e2e:im-math`），**刻意复用桌面 e2e 的同一份 mock 回答**，于是两者构成同一输入的真 A/B：

```
mock-llm-math → 真 opencode → 真 Bridge（SSE + BlockChunker + send）→ 抓到的四家出站文本
```

14 项断言全绿，含：巨型 display 公式整块降级未被分块切开 · 围栏里的 `f"${x}"` 逐字不动 · **四家渠道拿到逐字节相同的文本**（这正是把代码放 `bridge.send()` 而不是四个 adapter 的理由，第一次被真正验证）· 出站文本二次降级是不动点。

> **空转陷阱第三次出现**：首跑时 opencode 少配 `OPENCODE_APP_NAME`，回合报 "No provider available"，出站只有一句 51 字符的错误消息 —— 而「没有残留 LaTeX」「四家一致」「幂等」**4 条断言全绿**。已加 check 0 非空转门（不过就 `exit 1`）。conventions §19 那条教训**换个场景又踩一次**。

### 13.2 抓出的缺陷一：`\href` 静默吞内容

`\href{https://x}{点我}` 经 KaTeX 出来是 `\href` 四个字符，**「点我」没了**。根因是 KaTeX 对 `trust` 门控的命令**不抛异常**，而是把命令名按 `errorColor` 上色渲染。

- 判据必须用 KaTeX 自己的信号（`errorColor` 设哨兵色 + 树里检测），**不能扫输出里的反斜杠** —— `a \backslash b` 合法地渲染成 `a\b`，会被误杀。
- 修法方向安全：当作解析失败 → 保留原文 → 用户看到 `$\href{...}{点我}$`，即 P2 之前的行为。
- 固化 gotchas §18。

### 13.3 抓出的缺陷二：重新追问绕过了降级漏斗

答案格式错误时的重新追问（`answerPendingQuestion`）走 `msg.reply` **直发**，绕过 `send()` ⇒ 同一个问题第一次显示是降级的、重问时变回 `$\frac{1}{M}$` 源码。

不能简单改成 `this.send()`：adapter 的 `reply` 绑定在**具体那条入站消息**上，而 `send` 用的是本回合最初那条 —— 群聊里会回错上下文。故在该处显式调一次降级，并注释说明这是唯一无法走漏斗的出站点。（配套单测已验「回退修复即变红」，不是空转。）

### 13.4 对抗性探测结果

| 维度 | 方法 | 结果 |
|---|---|---|
| ReDoS / 病态输入 | 20k 上限下的 8 种病态串（2 万个孤立 `$`、永不闭合的 `$$`、1 万组真公式、2 万反引号…） | 最慢 **22ms**，无回溯爆炸。无 `$` 的文本走快速路径 0.1ms |
| KaTeX 宏炸弹 | billion-laughs（`\def` 四层嵌套 10^4 展开） | 被 KaTeX `maxExpand` 拦下 → null → **保留原文** |
| 深嵌套 | `\frac` 嵌 200 层 | 6.4ms 正常输出 |
| 幂等性 | 300 个随机组合各降级两次 | **0 个非幂等** |
| 无损性 | 1000 个不含 `$` 的随机串 | **0 个被改动**（逐字节相同） |
| 结构边界 | 未闭合块/行内、`$$$$`、`$ $`、4 反引号围栏、`~~~` 围栏、双反引号 code、引用/列表/粗体内公式、相邻两 span、emoji | 全部符合预期 |
| CRLF | 同一份文本的 LF 与 CRLF 版本 | 围栏跳过均正确（JS 的 `$` 在 `m` 模式下也匹配 `\r` 前，原以为有 bug，**实测没有** —— 幸好测了没瞎改） |

### 13.5 把「货币误伤」这条风险从推断变成实测

P2 让 IM 跟随桌面端一起承担 `$` 歧义。两个问题必须分开答：

**(a) 这是新增风险还是继承风险？** 拿 6 个 shell/路径场景跑**桌面端真实管线**：

```
运行 $env:PATH 查看，再看 $env:HOME   → 桌面端 katex=1，显示 "运行 env:PATH查看，再看env:HOME"
执行 echo $HOME 然后 echo $USER       → 桌面端 katex=1
路径 C:\Users\me\a$b$c\x.txt          → 桌面端 katex=1
变量 ${HOME} 与 ${USER}               → 桌面端 katex=1
价格 $5 和 $10                        → 桌面端 katex=1
Makefile 里 $(CC) 和 $(LD)            → 桌面端 katex=1
```

**六个桌面端全都已经当公式渲染了，损坏形态与 IM 侧逐字相同** ⇒ P2 是**继承**已发版并通过真机验收的取舍，不是新增 IM 独有损坏。（对比 §12.3 的 URL：那个桌面端**不**损坏，所以必须修。判据就是这条。）

**(b) 在本项目这种「编码 agent」语境下有多严重？** P0 语料全是中文数学题，不能外推。改用**本仓库自己的 225 个 md / 2.45M 字符**真实技术中文文档当代理语料：

| 指标 | 值 |
|---|---|
| 扫描 | 225 个 md，2455k 字符 |
| 被改动的文件 | **2** |
| 被误转换的 span | **3**（`$PATH」…$`、`$SHELL -lic 'printf <sentinel>$`、`${directory ?? ""}\|$`） |

约 **1.2 处 / 百万字符**。三处全是 shell `$` 那一类。⚠️ 注意语料偏乐观：文档里的命令大多进了反引号/围栏，正是这一点保护了它们；聊天回复没这么规矩。

**(c) 白名单方案的代价（另一侧）**：若改成「span 内容须含 `\ ^ _ { }` 才降级」，对 279 个真实公式的漏报是 **82 个（29.4%）**，全是 `$q(x)$`、`$M$`、`$P$` 这类单符号 —— 漏报的后果是显示原样 `$q(x)$`（= P2 之前的行为，安全方向）。

⇒ **当前定稿维持无白名单**（与桌面端一致），把上表作为将来若要反悔的决策依据。

### 13.6 钉钉/企微 `_` 风险的精确量化（唯一未闭合项）

此前只写「产物里的 `_(…)` 可能被对方渲染器当强调配对」，没有量级。实测 P0 语料：

| 指标 | 值 |
|---|---|
| 降级后含 ASCII `_` 的公式 | **27 / 279（9.7%）** |
| 降级后含 **≥2 个** `_` 的回答（才可能被配成一对） | **9 / 24（37.5%）** |

典型样本：`∇_(θ)J(θₜ)`、`D_(KL)(P∥Q)`。⇒ **这不是边角，是数学类回答里三分之一都会命中**，真机验收必须专门测。

按 CommonMark 规则它是安全的（`_` 前是字母、后是 `(`，不构成合法 opener），微信侧也已由 `stripMarkdown` 的 intraword 保护覆盖；风险只存在于**用裸正则做强调的非合规渲染器**，而钉钉/企微属不属于这一类**没有离线证据**（gotchas §4 未记载）。

若真机确认受损，两条候选修法各有代价，**都不要先斩后奏**：
- **A：下标回退改用下标括号** `∇₍θ₎` / `D₍KL₎` —— 彻底消除 markdown 活性字符，观感也更好；代价是 U+208D/U+208E 在部分 Android/Windows IM 客户端可能缺字形显示成豆腐块，**那比 `_` 更糟**，且同样只能真机验。
- **B：仅对钉钉/企微把 `_` 转义成 `\_`** —— 但微信/飞书是纯文本，会漏出字面反斜杠 ⇒ 必须按渠道分支，破坏「一处漏斗」的设计。

### 13.7 降级会不会引入 markdown 活性字符（实测）

| 输入 | 输出 | 活性字符 |
|---|---|---|
| `a * b` / `a \ast b` | `a∗b` | 无（KaTeX 出的是 U+2217，不是 ASCII `*`） |
| `x_1 + y_2` | `x₁+y₂` | 无 |
| `` \text{`code`} `` | `‘code‘` | 无（KaTeX 把反引号映射成左引号） |
| `\text{#标题}` | null | 无（`#` 在 KaTeX text 模式非法 → 保留原文） |
| `\text{**粗**}` | `**粗**` | `*` |
| `\text{[x](http://y)}` | `[x](http://y)` | `[]()` |

后两行确实会把 markdown 语法带出公式，但**内容是模型自己写的**，模型在公式外本来就能直接写同样的 markdown ⇒ 不构成新的能力或攻击面。唯一由**降级机制自身**引入的活性字符是下标回退的 `_`（见 §13.6）。

### 13.8 补最后一段：编译后 sidecar 的黑盒验证

§13.1 的 e2e 仍是 **import `bridge.ts` 源码**。客户装到机器上的是 `bun build --compile` 出来的 `channel-gateway-<triple>` —— 打包层（依赖是否内联、正则特性是否还在、模块能否解析）从源码完全看不见。

微信 adapter 的 ilink `baseUrl` 来自渠道配置 ⇒ 可以指向本地。于是**不接触任何真实 IM 账号**也能做真黑盒：

```
mock ilink server ──getupdates──► 编译后的 gateway 二进制
                                    │ （真 ChannelManager + 真微信 adapter
                                    │   + Bridge + send() + stripMarkdown）
                                    ▼
                                 真 opencode ──► mock-llm-math
                                    │
   抓 POST /ilink/bot/sendmessage ◄─┘   ← 断言打在这里
```

`e2e/im-math-sidecar-blackbox.e2e.ts`（`e2e:im-math-blackbox`），**13/13 通过**。它额外锁住三件源码级测试锁不住的事：

1. **`stripMarkdown` 的 intraword 保护在编译产物里真的生效** —— 断言 `D_(KL)` 完整送达（`\p{L}` + lookbehind 经 `bun build --compile` 后仍可用）。
2. **降级与 `stripMarkdown` 的先后顺序**：微信是纯文本，`stripMarkdown` 会拆掉行内 code 的反引号 ⇒ `` `$PATH` `` 到达时已是裸 `$PATH`。它没被当成公式，正是因为**降级跑在前面、那时反引号还在**。首版断言把这个正确结果误判为「LaTeX 残留」，改成正向断言后反而把这条顺序保证钉住了。

### 14.3 一个方法论教训：**粘贴链路本身会篡改证据**

中途我依据用户粘回来的企微文本判定「企微把 `_` 配对了」——**那是错的**。截图显示企微渲染完全正确。丢失发生在**粘贴的中转环节**：企微那一行恰好是 `D_(KL)(P∥Q)=∑_(x∈X)`，**同一行一对下划线**，被中转环节当成斜体标记消费掉了；而钉钉那条每行只有一个 `_`，配不成对，所以粘贴无损。

> **验证 markdown 相关行为时，粘贴过来的文本不是证据 —— 它经过了另一个 markdown 渲染器。**必须要截图，或者拿发送端的字节做对照。讽刺的是，我要找的那个失败模式真的发生了，只是发生在证据链上而不是被测系统里。

这条与「终端输出会被污染，核实必须查事实本身」是同一类问题的不同表现。
