# 开发收尾与交接

1. 读取仓库约定、当前变更及 `docs/stdd/git-workflow.md`。从任务、PR 或变更记录确定当前分支、真实合入目标和远端；功能分支的 upstream 不一定是合入目标。检查工作区及正在进行的 Git 操作，保留已有改动，记录同步前 HEAD 和目标。仅做中途交接、无远端或项目另有同步策略时按该范围执行，并标明同步状态。
2. 准备提交或 PR 时，默认先 fetch 已确认的目标远端，解析并固定本轮目标 SHA，再判断提交关系。已包含目标时跳过；仅落后时快进；存在分叉时，将未发布的本次提交或项目允许改写的个人分支 rebase 到目标 SHA。执行前确保工作区可安全整理、保存恢复点，并核对分支共享状态。具体命令和例外见 `docs/stdd/git-workflow.md` 的「收尾同步」。fetch 失败或目标不明时，不能把旧引用当作已同步；其他独立检查可以继续。
3. rebase 冲突时逐文件核对双方修改、规格和场景 ID，在已确认范围内解决，检查后 `git add <已解决文件>`、`git rebase --continue`，直到完成。不能用整批 ours/theirs 或跳过提交代替判断。遇到业务口径矛盾或无法保留双方意图时，留下冲突文件、双方意图、已完成步骤和继续或撤回入口，只请求缺少的决定，不继续提交或推送该候选。
4. 同步实际交付的规范、契约和任务。按 `docs/stdd/decisions-and-discussions.md` 关联讨论与生效 ADR，将可复用的新约定写回项目已有工程文档。已有变更日志片段约定时沿用其位置。按项目流程归档，校正变更、讨论、ADR 和入口之间的链接；重复收尾不重复追加相同结论。
5. 在同步、冲突处理及约定的提交整理后，先恢复本次临时保存的改动并处理恢复冲突，再按锁文件和项目命令同步发生变化的依赖。重新核对候选差异，运行定向验收及适用的构建、lint 和回归。沿用项目的测试层级，不固定只跑单元测试。将目标 SHA、受测 HEAD 或工作区差异、命令、用例数量、实际结果和未验场景写入 `verification.md`；只更新报告时注明它对应的受测内容。必跑检查失败或必验场景缺证据时，按项目约定标记未就绪。
6. 使用 PR 模板准备范围、确认依据、同步状态、验收证据、影响和下一步。squash 沿用项目策略，优先由合入流程完成；本地整理限已授权范围，整理后核对证据仍适用。提交、推送、创建 PR 和发布按任务已有授权执行，不因调用收尾技能扩大授权。推送时若发现远端继续前进，重新核对并同步、复验；同一原因持续阻塞时交代恢复入口，避免重复改写或强推。
